# build-headless-integration-mcp

A standalone MCP server that renders Mule flow XML inline as an interactive
React Flow canvas in Claude Desktop. Companion to the
[`build-headless-integration`](../SKILL.md) skill.

## What it does

After the skill writes `<projectDir>/src/main/mule/<name>.xml`, the agent
calls one MCP tool:

```
render_mule_flow(project_dir="/abs/path/to/project")
```

The tool:
1. Parses the flow XML into a `{nodes, edges}` graph (one node per top-level
   processor, containers like `<choice>`/`<try>` collapse to a summary node).
2. Returns the graph as a `TextContent` block plus a `ui/resourceUri` hint.
3. Claude Desktop fetches the bundled HTML resource and renders an iframe
   inline in the chat with React Flow + dagre.

Click any node in the canvas to see its XML attributes in a side panel.
The canvas is read-only in v1 — edits go through the chat.

## Prerequisites

- Python 3.11 or later (`/opt/homebrew/bin/python3.12` works on macOS).
- The `build-headless-integration` skill (this directory's parent) — the MCP
  server reads project layout the skill produces.
- Claude Desktop with MCP support enabled.

The MCP server itself has no Docker dependency (the skill's `ensure_rds.sh`
handles that for the parent skill — the canvas just reads files on disk).

## Install

### 1. Editable install into a Python environment

From the skill's `mcp/` directory:

```bash
SKILL="$HOME/Salesforce/workspace/mulesoft-dx/skills/mule-development/build-headless-integration"
cd "$SKILL/mcp"

# Create a dedicated venv (recommended). Replace python3.12 with your 3.11+ binary.
python3.12 -m venv .venv
source .venv/bin/activate

pip install -e .
```

Editable (`-e`) means edits to `parse.py`, `server.py`, or any of the
`ui/*` files take effect on the next tool call without reinstalling. The
console script `build-headless-integration-mcp` lands in the venv's `bin/`.

### 2. Register with Claude Desktop

Open `~/Library/Application Support/Claude/claude_desktop_config.json` (or
the equivalent path on your platform) and add an entry under
`mcpServers`. The `command` must be the absolute path to the venv's
console script (NOT `build-headless-integration-mcp` on its own — Claude
Desktop launches with a minimal PATH):

```jsonc
{
  "mcpServers": {
    "mule-flow-canvas": {
      "command": "/Users/<you>/Salesforce/workspace/mulesoft-dx/skills/mule-development/build-headless-integration/mcp/.venv/bin/build-headless-integration-mcp"
    }
  }
}
```

If you have other MCP servers configured, just add this entry alongside.

### 3. Restart Claude Desktop

Quit fully (⌘Q) and re-open. The first time the app starts, it spawns the
MCP server over stdio and discovers the `render_mule_flow` tool. To
verify, in a fresh chat:

```
What MCP tools do you have access to?
```

You should see `render_mule_flow` listed.

## Smoke test

With the MCP server installed and a project already generated by the
parent skill:

```
> Render the flow at $HOME/Salesforce/projects/headless/sf-accounts-to-twilio
```

The agent calls `render_mule_flow(project_dir=...)` and Claude Desktop
shows the canvas iframe inline — trigger node at the top, processors
flowing down, error-handler at the bottom, click-to-expand attributes in
the side panel.

If the canvas doesn't render:

- **"Tool not available"** — the MCP server isn't registered or didn't
  start. Check `~/Library/Application Support/Claude/Logs/` for the
  startup error. Common cause: wrong `command` path in
  `claude_desktop_config.json`.
- **"React Flow failed to load"** — the iframe couldn't fetch CDN
  scripts. v1 loads React/ReactFlow/dagre from `unpkg.com` /
  `cdn.jsdelivr.net`; if your network blocks those, file an issue and
  we'll switch to inlined bundles.
- **"No flows found"** — the XML at `<project_dir>/src/main/mule/*.xml`
  has no `<flow>` or `<sub-flow>` elements. Check
  `validate_generated_flow_xml.sh` output first.

## Development

Run the parser test suite:

```bash
cd "$SKILL/mcp"
source .venv/bin/activate
pip install -e ".[dev]"
pytest
```

Iterate on the canvas (`ui/app.html`, `ui/app.css`, `ui/app.js`):

- Editable install means you don't need to reinstall.
- `_serve_app_html()` composes the document on every request, so the
  next `render_mule_flow` tool call picks up your changes — no Claude
  Desktop restart needed for UI tweaks.
- Server-side changes (`parse.py`, `server.py`) require restarting the
  MCP process. Quit Claude Desktop and re-open, or run a quick
  one-liner from the parent skill to validate without involving the host:

  ```bash
  python -c "
  from build_headless_integration_mcp.parse import parse_flow_xml
  import json
  print(json.dumps(parse_flow_xml('/path/to/flow.xml'), indent=2))
  "
  ```

## Architecture

```
Claude Desktop chat
   │
   │ tool call: render_mule_flow(project_dir=...)
   ▼
build-headless-integration-mcp  (this server, FastMCP over stdio)
   │
   ├── parse.py       Mule XML  ─►  {nodes, edges}
   │
   └── ui/app.html    bundled HTML resource
       ├── app.css    minimal Mule design tokens
       └── app.js     React + ReactFlow + dagre + side panel
   │
   ▼ TextContent (graph JSON) + meta.ui/resourceUri
   │
Claude Desktop iframes ui://mule-flow-canvas/app.html
   │
   ▼ postMessage {method: "ui/notifications/tool-result", params: {...}}
   │
app.js parses the JSON graph and renders the React Flow canvas
```

The server is intentionally narrow: one tool, one resource, no auth, no
persistent state. It's a viewing surface — not a backend service.

## What's NOT in v1

These would extend scope significantly; treating them as v2 work.

- **Nested layout for containers** — `<choice>`, `<try>`, `<scatter-gather>`
  collapse to one summary node. Real nesting (the way the vscode canvas
  renders them) needs a layout engine port from
  [mule-dx-mule-dev-vscode/src/views/xml-editor/](file:///Users/tzeree/Salesforce/workspace/mule-dx-mule-dev-component/mule-dx-mule-dev-vscode/src/views/xml-editor/).
- **Edit nodes from the canvas** — read-only; chat is the editing surface.
- **Test Connection from the canvas** — go through the chat or open the
  project in ACB.
- **Connector icons** — generic kind badges (trigger/processor/container/
  error-handler) instead of per-connector icons. Reusing the vscode SVG
  pack is a one-day-extra task once we know layout is stable.

If a user request needs one of these, route it through chat and let the
agent regenerate the project — same source of truth either way.
